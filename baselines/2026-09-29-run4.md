**This closes the question run3 left open.** Run3 observed that Voice-Flow's five `ask`
patterns key on colon-separated npm script names (`install:app`) while the scripts they
run are hyphen-separated filenames (`install-app.js`), and that a string containing one
does not contain the other. It called that *"a hypothesis about coverage, not a
demonstrated bypass"*, and declined to confirm it by running a real script. Run4 does not
confirm it either. It takes the other route: four `ask` patterns keyed on the **file**
spelling were added, and each was then observed to prompt.

## The four rules added

```json
"Bash(*scripts/install-app*)",
"Bash(*scripts/compile-vault*)",
"Bash(*scripts/reset-permissions*)",
"Bash(*scripts/uninstall-app*)"
```

The `scripts/` prefix is load-bearing in two places. `uninstall-app` contains the substring
`install-app`, so a bare `*install-app*` would have fenced the uninstaller as a side effect;
`scripts/uninstall-app` does not contain `scripts/install-app`. And electron-builder ships
an `install-app-deps` binary, which a bare pattern would also have reached.

## The probes

Each is a harmless `grep -c` against `package.json`. Nothing reads, spawns or executes any
of the four scripts — the path appears only as a search pattern.

```
Ask rule Bash(*scripts/reset-permissions*) overrides auto mode for this command.
```

### Probe 3 needed a second attempt, and why that matters

On the first pass, probes 1, 2 and 4 prompted but probe 3 showed **no box** — because that
session's Claude declined to submit the command at all, having had two commands denied
before it. The permission engine was never reached. That is a null result, not a failure,
and treating it as evidence the rule did not fire would have been wrong.

It was re-run as the **first and only** command in its own fresh session, and prompted. The
method note worth keeping: a probe that must observe a prompt has to be the first thing in
a session, because a prior decline suppresses the submission rather than the rule.

## What this shows

Scoped to those four exact `grep -c` commands and nothing wider:

1. All four newly added `ask` patterns match and prompt.
2. **Leading-`*` substring matching works** in the Bash matcher. Until now this repo had it
   from the shape of the global list and one 2026-09-20 probe; here it is observed against
   a project's own rules.
3. **An `ask` overrides an `allow`.** `Bash(rtk grep *)` is in the *global* `allow` list and
   these commands still stopped. `ENVIRONMENT.md` asserted this; it had not been probed.
4. **An `ask` overrides auto mode**, in the box's own words.
5. Each box names the rule that matched, so attribution is unambiguous.

## What this does not show

- **Nothing about real script execution.** No npm script and no Node script was run, here or
  by Amit. `install:app`, `compile:vault`, `reset:permissions` and `uninstall:app` act on
  the machine and the installed app, and running a destructive command to prove a prompt
  appears remains a bad trade.
- **Nothing about the two `--dry-run` `allow` entries.**
  `Bash(node scripts/reset-permissions.js --dry-run)` and
  `Bash(node scripts/uninstall-app.js --dry-run)` are both matched by the new patterns and
  are predicted to start prompting. Predicted, not observed.
- **Nothing about child processes.** These scripts run `ditto`, `codesign`, `security`,
  `osascript`, `tccutil`, `pkill` and `lsregister` inside a Node process, not as Bash
  commands. No rule was exercised against that path.
- **Nothing about other wrappers.** One `rtk`-prefixed form was observed. `sh -c`, `env …`
  and bare invocation were not.
- **One spelling is not covered by these four rules at all:**
  `cd scripts && node install-app.js`. It matches no rule in any of the four settings files,
  before or after this change. Known, not fixed.

## Interpretation — Claude's, not verified

Run3's colon/hyphen hypothesis is neither confirmed nor refuted by run4, and deliberately
so. Run4 sidesteps it: rather than proving the old patterns had a hole by running something
destructive through it, it added patterns keyed on the file spelling and showed those fire.
If the hypothesis was right, the hole is now closed for the four paths named. If it was
wrong, the cost is four redundant rules, which only ever add a prompt.

The `--dry-run` prediction follows from finding 3 above rather than from a separate
observation, and `ENVIRONMENT.md` records that argument-constrained `allow` patterns have
not held reliably in the past. Both `--dry-run` entries should be expected to prompt until
someone watches one.

The four probes were chosen to differ from each other in exactly one variable — the search
pattern — with the same verb, same file and same shape. That is why probe 3's re-run is
readable as testing the rule rather than testing the session.
