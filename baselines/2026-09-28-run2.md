## Claude's wrong reading, and the correction

Claude first reported that no prompt had appeared, inferring it from having received `1`
as command output. **An output of `1` is not evidence that no prompt occurred** — the
prompt had fired and Amit had approved it. Claude then built a causal story to explain a
silence that never happened, and found out only because Amit said he had seen the prompts.
Claude corrected itself in the same session.

Recorded because the error is the reusable part: **Claude cannot see permission prompts,
and must never infer "no prompt" from receiving output.** The standing note is
`projects/-Users-amitjangra-Documents-VS-Code-Voice-Flow/memory/cannot-see-permission-prompts.md`.

## What this shows

Five harmless `rtk grep` commands matched five project `ask` patterns in a Voice-Flow
auto-mode session, and each prompt named its matching rule. Those five rules were
therefore in force in the running session.

## What this does not show

- **FinNode's three entries** — different file, different project. Not tested.
- **The real npm scripts.** The string matched inside a `grep`. `npm run compile:vault`
  was never run, and must not be run to find out whether it matches.
- **Direct `node scripts/…` and `sh -c` spellings.** Not tested, and they may not match
  these patterns. A command Claude issues through Bash does reach Claude Code's permission
  system whatever its spelling; whether a given pattern matches that spelling is a
  separate question, and an untested one here.
- **Anything Amit types himself in Terminal.** That does not go through Claude Code at
  all, so no permission rule can reach it. Only a confirmation inside the script can.
- **Mirror currency.** Five rule names in force in one session says nothing about the
  other mirrored files, or about every script entry point.
- **A designed approval-through-handoff workflow.** Steps 4 and 7–9 of the task order —
  approve, review, record, handoff — were not demonstrated. This was a permission probe,
  not a workflow test.
